# 7. Вики — продуктовая база знаний (правила наполнения и обновления)

`7. Вики/` — **human-facing** база знаний: «что есть в системе и как этим пользоваться». Аудитория: маркетологи, менеджеры, тех-поддержка, обучаемые пользователи, новые разработчики.

## Вики ≠ 2. Модули

| | `7. Вики/` | `2. Модули/` |
|---|---|---|
| Аудитория | люди (маркетинг/менеджер/юзер/поддержка) | Claude / разработчик |
| Отвечает на | «что это и как пользоваться» | «как устроено в коде» |
| Язык | простой, без жаргона, по шагам | технический (модели, эндпоинты, бизнес-правила) |
| Когда читать | онбординг, обучение, маркетинг | **перед правкой кода модуля** |

Не смешивать. Вики описывает ПРОДУКТ; `2. Модули` описывает РЕАЛИЗАЦИЮ.

## Структура (разделы по аудиториям)

> Разделы опциональны и адаптируются под проект. Минимум для продукта с пользователями: `00 — Индекс` + `A` + `B`.

| Раздел | Содержимое | Аудитория · тон |
|---|---|---|
| `00 — Индекс.md` | Карта вики, таблица «аудитория → раздел», источники, история версий | все |
| `A. Для сайта/` | Pitch, фичи-преимущества, сравнение с конкурентами, аудитория/use-cases, тарифы, FAQ, готовые тексты лендинга | маркетинг/продажи · продающий |
| `B. User Guide/` | Пошаговые инструкции по каждому модулю (быстрый старт → продвинутое) + FAQ юзера | конечный пользователь · дружелюбный |
| `C. Сценарии и процессы/` | Сквозные кейсы через несколько модулей (для обучающих видео и helpdesk) | поддержка/обучение |
| `D. Техническое состояние/` | Обзорная тех-картина: архитектура, API, БД, деплой, тесты, дизайн-система | разработчик/DevOps/due-diligence |
| `E. Связи и зависимости/` | Карта модулей, data flow, cron/фоновые процессы | разработчик/PM |
| `F. Бренд и дизайн-система/` | Бренд SSOT: лого, цвета, типографика, voice, a11y | дизайнер/маркетинг |

## Frontmatter Вики-файла

```yaml
---
title: ...
type: wiki | wiki-index
audience: marketing | user | support | dev | devops | pm | designer | all
status: active | draft | archived
created: YYYY-MM-DD
updated: YYYY-MM-DD
related: ["[[…]]"]
owner: ...
---
```
Ключевое отличие — поле **`audience`** (для фильтрации и навигации).

## Когда писать / обновлять Вики

| Триггер | Куда писать |
|---|---|
| Фича стала доступна пользователям (released) | статья в `B. User Guide/` (+ `A` если влияет на позиционирование) → обновить `00 — Индекс` |
| Изменился пользовательский сценарий / UX | обновить релевантную статью `B`/`C` |
| Изменилась цена / позиционирование / конкуренты | `A. Для сайта/` |
| Существенно изменилась архитектура / API / стек | `D. Техническое состояние/` (обзорно; детали — в `2. Модули`) |
| Новый модуль/раздел продукта | новая статья нужного раздела + строка в `00 — Индекс` |
| Онбординг / обучение новой роли | читать нужный раздел по аудитории (писать не обязательно) |

## Принципы (по рабочему эталону)

1. **Каждый файл самодостаточен** — открыл отдельно, понял без соседей.
2. **Перекрёстные `[[ссылки]]`** — Obsidian строит граф.
3. **Frontmatter с `audience` обязателен.**
4. **Дублирование между разделами допустимо** — у `A`/`B`/`C` разные цели и аудитории.
5. **Маркетинг (A) ≠ User Guide (B):** `A` продаёт («экономьте 20%»), `B` учит («нажмите ⊕»).
6. **При обновлении статьи** — поднять `updated` и дописать строку в «История версий» индекса.
7. **Источник правды о коде — `2. Модули`/код.** Раздел `D` Вики — производная обзорная картина, не дубль внутренней документации.

## Питается из (источники)

`1. Проект/` (обзор, аудитория) · `2. Модули/` (тех-детали) · `5. Планы/` (roadmap, конкуренты, монетизация) · `6. Справочник/` (дизайн-система) · project CLAUDE.md/README (правила, quick start).
