# Routing Matrix — когда какую папку vault читать и куда писать

Ядро Brain Protocol v3.0. Цель — убрать «неявность»: для каждого триггера явно сказано, что ПРОЧИТАТЬ до работы и что ЗАПИСАТЬ после.

## Матрица

| # | Триггер | ЧИТАТЬ до | ПИСАТЬ после |
|---|---|---|---|
| 1 | Старт сессии / «продолжай / дальше» | `4. Активная работа/SESSION_STATE.md`; если контекст новый — `1. Проект/` | — |
| 2 | Перед правкой существующего модуля | `2. Модули/<модуль>` + свежие записи `3. Журнал/ГГГГ-ММ/` по нему | — |
| 3 | Реализация фичи / нового кода | **grep по кодовой базе** + `2. Модули/` + релевантное в `5. Планы/` | — |
| 4 | Завершён осмысленный юнит работы | — | запись в `3. Журнал/ГГГГ-ММ/`; если модуль изменился — обновить `2. Модули/<m>`; если сдвинулся объём/план — `5. Планы/` |
| 5 | Новый модуль / подсистема | `1. Проект/` + `6. Справочник/` (паттерны) | новый файл `2. Модули/<m>` + при необходимости паттерн в `6. Справочник/` |
| 6 | Принято решение / трейдофф | — | строка в STATE «Решения» + (если важно) запись в `3. Журнал/` |
| 7 | Каждый значимый шаг / ~5 сообщений | — | обновить STATE (frontmatter `last_updated`, строка `→ Следующий шаг:`) |
| 8 | Сдвиг плана / объёма / приоритетов | `5. Планы/` | `5. Планы/` + поднять флаг ревью-гейту/пользователю |
| 9 | Баг найден (даже если не чиним сейчас) | — | запись в `5. Планы/` (или баг-файл) |
| 10 | После сжатия контекста | STATE → `3. Журнал/[месяц]` → WIP `4.` | продолжить со строки `→ Следующий шаг:` |
| 11 | Фича стала доступна юзерам / смена UX | — | `7. Вики/B. User Guide` (+ `A. Для сайта` если влияет на позиционирование) + `7. Вики/00 — Индекс` |
| 12 | Смена цены / позиционирования / конкурентов | `5. Планы/` | `7. Вики/A. Для сайта` |
| 13 | Онбординг / обучение новой роли | `7. Вики/` (раздел по аудитории) | — |

Правила наполнения `7. Вики/` (human-facing база знаний, ≠ `2. Модули`) — см. `wiki-guide.md`.

## Примеры

**Правка модуля авторизации:**
1. (триггер 2) читаю `2. Модули/Auth.md` + последние записи `3. Журнал/` про auth.
2. (1.5) grep по коду — нет ли уже нужной функции.
3. правлю точечно (`Edit`, не переписываю файл целиком).
4. (триггер 4) запись в `3. Журнал/ГГГГ-ММ/ГГГГ-ММ-ДД — auth fix.md`, обновляю `2. Модули/Auth.md`, двигаю `→ Следующий шаг:`.

**Старт большой фичи:**
1. (триггер 5) читаю `1. Проект/` (архитектура) + `6. Справочник/` (паттерны).
2. план фаз → `5. Планы/ЭПИК — …md`; «Сейчас» + первая `→ Следующий шаг:` → STATE, остальные фазы → «Очередь».
3. по ходу — триггеры 4/6/7.

## Запреты (часть ядра)

- ❌ **Второй SESSION_STATE** не создавать. Он один. При реорганизации vault файл `mv`, старое — в `_state_backups/`.
- ❌ **Не раздувать STATE** — завершённое уходит в `3. Журнал/`, STATE остаётся компактным.
- ❌ **Чужой vault** не трогать (определяется по `.claude/brain.conf` текущего проекта).
- ❌ **Готовые файлы — только точечные правки**, без широких «redesign/cleanup» проходов: они затирают прежние правки.
- ❌ **План — в STATE/Планах, не в голове контекста** (контекст сожмётся).

## Принцип конфликта

При расхождении «контекст ↔ vault» — **побеждает vault** (он durable). Если vault устарел — сначала обнови vault, потом действуй.
